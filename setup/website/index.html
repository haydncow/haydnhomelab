Four times I had to think on my feet

Four real problems from building my lab: what happened, what I did about it and how it turned out.

21 October 2026Vulnerability management and incident response

An NCSC warning, handled the same day

Situation
The NCSC warned about two critical PHP flaws that could let an attacker run their own code on a web server.
Task
Find out if anything on my Pi used PHP, and deal with it before it could be exploited.
Action
I checked each service instead of assuming. My site and Pi-hole don’t use PHP, but my Speedtest app’s container had PHP 8.5.11, from before the fix. No patched version was out yet, so I stopped it.
Result
The risk was gone the same day. When PHP 8.5.12 came out, I checked the new image’s version before starting it again.

Read the write-upMITRE ATT&CK T1190

23 October 2026A real attack, and reading the evidence

Spotting a real attack in my logs

Situation
The day I added a blocked-request feed to my live lab, it showed a burst of requests I hadn’t made.
Task
Work out what it was after, and whether my defences held.
Action
I went through the evidence: the paths (phpinfo.php, .env and .bak files), the timing (dozens in about 10 seconds) and the source, a rented cloud server pretending to be Chrome on Windows.
Result
My Cloudflare rule blocked every request, and my site has no PHP anyway. It was a textbook wordlist scan.

Read the write-upMITRE ATT&CK T1595.003

27 October 2026Vulnerability management and automation

Scanning my own apps: 2 critical down to 0

Situation
The PHP alert showed me that Docker apps carry their own software, which can quietly go out of date.
Task
Find vulnerable software myself, every week, without drowning in noise.
Action
I set up Trivy to scan every app each Monday, only counting high and critical problems that already have a fix, with the result sent to my phone.
Result
First scan: 2 critical, 15 high. After updating and scanning again: 0 critical, 6 high, which are waiting on the apps’ makers.

20 October 2026Cryptography and risk

Finding a weak spot in my own backups

Situation
My nightly backups held my VPN key, tunnel token and password hashes, unencrypted, on a USB drive.
Task
Keep them safe even if someone took the drive.
Action
I encrypted every backup with age. The Pi only has the public key, so it can lock backups but not open them. The private key stays on my Mac and in my password manager.
Result
A stolen drive is useless now. I proved a restore works (the SHA-256 hashes matched), then shredded the old unencrypted backup.

My DNS refuses faked answersLooked up a domain with broken signaturesRefused20 Oct

Pi-hole blocks ads, trackers and known malware domains on my devices. Unbound looks websites up itself instead of telling one big company every site I visit, and checks DNSSEC, so a domain with deliberately broken signatures gets refused.

Honeypot write-up

My backups can actually be restoredDecrypted one on my Mac and compared itSHA-256 matched20 Oct

Every night the Pi backs up its settings, scripts, Jellyfin and Pi-hole to the 1TB drive, encrypted, and keeps the last 14. A backup is only useful if you can restore it, so I decrypted one on my Mac and compared it with the real file.

  1. The Pilocks each backup with the public key. It can’t unlock it.
  2. 1TB driveonly ever holds encrypted .age files.
  3. My Macunlocks it with the private key, which never touches the Pi.
  4. Checkthe SHA-256 of the restored firewall rules matched the Pi’s.

Things that broke, and how I fixed them

I learned the most from things going wrong. These are the ones I’m proudest of working out.

What brokeWhyWhat I did
I locked myself out of the PiI’d copied my old SSH key to the Pi, then made a new one. With passwords off, nothing could log in.Reflashed it and did it in the right order: copy the key, check it works, then turn passwords off.
My site worked on my Mac but nowhere elseI’d typed “http” into Cloudflare’s subdomain box, so the record was http.haydnhomelab.com.Fixed the DNS record, then cleared the old answers my devices had saved.
My rate limit didn’t block anythingI’d matched the path /, which only covers the homepage.Changed it to /* and tested again: 785 of 1,000 requests blocked.
Cloudflare kept showing “bad gateway”Python’s simple web server couldn’t keep up with the page asking for new data every 3 seconds.Swapped it for Caddy, a proper web server.
My stats worked by hand but not on a scheduleCron runs with a short PATH that doesn’t include /usr/sbin, where ufw lives.Found it in the error log, then set the full PATH in the script.
My 1TB drive vanished after a restartThe USB storage driver hadn’t loaded, so Linux couldn’t see the drive at all.Loaded it with modprobe, then made it load on every boot.
The honeypot kept crashingIts start script uses sudo, and my sandbox blocks that on purpose.Ran it directly as its own user, so it doesn’t need root at all.
Lynis said I had no security updatesDebian 13 uses a newer sources format that this version of Lynis can’t read.Checked by hand. The updates were there, so it was a false positive.
I nearly put my own email on my public siteI’d typed it into the honeypot’s fake login while testing it.Changed the page to only show common attacker usernames.
