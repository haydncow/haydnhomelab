What I’ve built, and how I proved it works

I didn’t want to set things up and just hope they worked. For each part I found a way to prove it, usually by attacking it myself. Each one links to the full write-up on GitHub. I’ve hidden hostnames and IP addresses.

Only my key can log in

SSH is how I control the Pi remotely. I turned off password logins so only my SSH key works, stopped root logging in, and only allowed my own user. I locked myself out once getting there, which is in the fixes further down.

Tested 16 OctoberWrite-up
$ ssh -o PubkeyAuthentication=no haydn@<the pi>
haydn@<the pi>: Permission denied (publickey).

Forcing a password login gets refused straight away.

The firewall only shows what I opened

UFW blocks everything coming in unless I’ve allowed it. To check, I scanned all 65,535 ports from another computer on my network. Only the four I’d opened showed up.

Tested 17 OctoberScan results
$ sudo nmap -p- <the pi>
Not shown: 65531 filtered tcp ports (no-response)
PORT    STATE SERVICE
22/tcp  open  ssh
53/tcp  open  domain
80/tcp  open  http
443/tcp open  https

“Filtered” means the firewall drops the packet without replying, so a scanner can’t even tell anything is there. This scan was before I added more services.

Guess my password and you get banned

Fail2ban watches the login logs. Five wrong logins in ten minutes and that IP gets banned in the firewall for an hour, and for longer if it comes back. I tested it by attacking from my Kali Linux VM until it banned me, then unbanned myself.

Blocks ads, and keeps my lookups private

Pi-hole blocks ads and trackers on my devices, including my phone anywhere through Tailscale. Behind it, Unbound looks websites up itself instead of sending every lookup to Google or Cloudflare. It checks DNSSEC signatures too, so faked answers get refused.

Tested 20 OctoberWrite-up
# a domain with deliberately broken signatures
$ dig fail01.dnssec.works @127.0.0.1 -p 5335
;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL

# the same test site, signed properly
$ dig dnssec.works @127.0.0.1 -p 5335
;; ->>HEADER<<- opcode: QUERY, status: NOERROR
;; flags: qr rd ra ad

Output trimmed. Unbound refused the broken one. The ad flag on the real one means the answer was checked and is genuine.

A honeypot to catch anything poking around

OpenCanary pretends to be eight services that nothing should ever touch, so any connection to them is a warning sign. It runs as its own user with no login, in a locked-down sandbox, on my home network only.

While testing it, I noticed what I typed into the fake login would show on my public dashboard. So I changed it to only ever show common attacker usernames, never passwords or IP addresses.

Backups I’ve actually restored

Every night the Pi backs up its settings, scripts, Jellyfin and Pi-hole to the 1TB drive and keeps the last 14. A backup is only useful if you can restore from it, so I restored my firewall rules from one and compared them with the real file.

Restored 20 OctoberHow it works
$ sudo diff <restored copy>/etc/ufw/user.rules /etc/ufw/user.rules
$

No output from diff means the two files are identical, so the backup works.

Things that went wrong, and how I fixed them

I learned the most from things breaking. These are the ones I’m proudest of working out.

What happenedWhyWhat I did
I locked myself out of the PiI’d copied my old SSH key to the Pi, then made a new one. With passwords off, nothing could log in.Reflashed it and did it in the right order: copy the key, check it works, then turn passwords off.
My site worked on my Mac but nowhere elseI’d typed “http” into Cloudflare’s subdomain box, so the record was http.haydnhomelab.com.Fixed the DNS record, then cleared the old answers my devices had saved.
Cloudflare kept showing “bad gateway”Python’s simple web server couldn’t keep up with the page asking for new data every 3 seconds.Swapped it for Caddy, a proper web server.
My stats script worked by hand but not on a scheduleCron runs with a short PATH that doesn’t include /usr/sbin, where ufw lives.Found it in the error log, then set the full PATH in the script.
My 1TB drive vanished after a restartThe USB storage driver hadn’t loaded, so Linux couldn’t see the drive at all.Loaded it with modprobe, then made it load on every boot.
The honeypot kept crashingIts start script uses sudo, and my sandbox blocks that on purpose.Ran it directly as its own user, so it doesn’t need root at all.
Lynis said I had no security updatesDebian 13 uses a newer sources format that this version of Lynis can’t read.Checked by hand. The updates were there, so it was a false positive.
My rate limit didn’t block anythingI’d matched the path /, which only covers the homepage.Changed it to /* and tested again: 785 of 1,000 requests blocked.
I nearly put my own email on my public siteI’d typed it into the honeypot’s fake login while testing it.Changed the page to only show common attacker usernames.
