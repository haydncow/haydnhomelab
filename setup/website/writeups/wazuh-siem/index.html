I set up a SIEM and attacked my own Pi to see what it caught

I put Wazuh, a free SIEM, on my PC and sent it my Pi's logs. Then I attacked the Pi from Kali. It caught the password guessing and the honeypot, but missed the scan.

16 November 20264 min readBy Haydn
Goal
See attacks on my Pi in one place, as they happen
Result
Brute force and honeypot caught, scan missed
Tools
Wazuh, VirtualBox, Kali Linux, nmap, OpenCanary

What a SIEM is

My Pi already has defences: Fail2ban, CrowdSec, a honeypot and phone alerts. But each one keeps its own log, so to see what happened I'd have to check them one by one. A SIEM (security information and event management) collects logs in one place, reads them, and raises an alert when something looks like an attack. It's the main tool a SOC analyst works in every day.

I used Wazuh, which is free and open source. The server runs in VirtualBox on my PC (4 CPUs, 8GB of RAM), and a small agent on the Pi sends it the Pi's logs.

Setting it up

Wazuh gives you a ready-made virtual machine, so the server was mostly import and start. Then I installed the agent on the Pi and pointed it at the server:

$ sudo WAZUH_MANAGER="[server]" WAZUH_AGENT_NAME="pi" apt-get install -y wazuh-agent
$ sudo systemctl enable --now wazuh-agent
Active: active (running)

The agent connected, but my first test didn't show up. Debian 13 keeps logs in the system journal and doesn't write /var/log/auth.log any more, which is where the agent looks for logins. Installing rsyslog brought the file back, and the alerts started coming in.

Test 1: guessing my SSH logins

My Pi only accepts SSH keys, so I tried logging in a few times as a user that doesn't exist. Wazuh flagged each try, then spotted the pattern and raised a level 10 alert for brute force. It also matched it to MITRE ATT&CK by itself: password guessing, over SSH.

Test 2: an nmap scan

From my Kali Linux machine I ran a service scan against the Pi:

$ sudo nmap -sS -sV [pi]

It found the Pi in 28 seconds. Funnily enough, nmap decided my Pi was a Cisco router, because the honeypot's fake services fooled its guess.

But Wazuh showed nothing. A scan only knocks on ports, it never logs in, so nothing on the Pi wrote a log line about it. That was the biggest lesson of the night: a SIEM only sees what something logs.

Test 3: the honeypot

My OpenCanary honeypot already logs every connection to its fake services, but Wazuh wasn't reading that file. I told the agent to read it, then wrote my own rule on the server to turn each hit into a level 10 alert:

<!-- my rule: any connection the honeypot logs is an alert -->
<rule id="100200" level="10">
  <decoded_as>json</decoded_as>
  <field name="dst_port">^\d+$</field>
  <field name="src_host">\.+</field>
  <description>Honeypot: OpenCanary caught a connection to port $(dst_port) from $(src_host)</description>
  <mitre><id>T1046</id></mitre>
</rule>

Then I attacked the honeypot from Kali: a fake SSH login on port 2222 and a fake login on the NAS page on port 8081.

Both were caught within seconds, with the port and where the attack came from.

My own defences locked me out: I ran the first login test from my PC, so the Pi banned my PC. My PC uses the Pi's Pi-hole for DNS, so the ban took its internet down too, and SSH stopped working. Lifting the ban fixed it. It proved the defences work, but next time I'll attack from Kali, not the computer I need.

What's next

Wazuh also checked the Pi against the CIS Debian 13 security benchmark and scored it 49%. Raising that score is my next project.

What I learned

  • A SIEM is only as good as the logs it gets. No log line, no alert.
  • One failed login is noise. Ten in a row is an attack, and the SIEM can tell the difference.
  • Writing my own rule took a few lines, and it turned my honeypot into proper alerts.
  • Test attacks from a machine you don't mind getting banned.
